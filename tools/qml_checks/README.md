# qml_checks —— qmllint 管不到的那一半门禁

`tools/qml_lint.sh` 跑的是 qmllint，但 qmllint **解析不了 `CommonOptions` 和各个
`xxxService`**（它们是 `main.cpp` 用 `setContextProperty` 注入的上下文属性），
拼错属性名它一声不吭。这一半由本目录的 JS 检查器兜着。

- 默认扫描根目录 = 本文件所在目录的 `../../qml`（数据类检查器是 `../../assets/data`），
  所以从仓库任何位置都能跑；也可以传第一个参数指定别的根目录。
- 判读：`pragma/layout_prop/mono_cjk/icon_glyph/layout_collapse/crossfile_id/undefined_id/component_id_scope/int_prop/bound_model/singleton_import/controls_import/typed_member/delegate_shape/coord_metadata/filter_rebuild/bottom_clearance/state_truth/overlay_triad/user_text_marks/page_fill_check/page_head_check/climate_anchor_check/combo_shape_check/error_text/dialog_text_width/confirm_code`
  这 27 个是 **pass/fail 门禁，期望 0 条**（`error_text_check.js` 是唯一扫 `../../src` 的一道，其余扫 `qml` 或 `assets/data`）；
  后 3 个是**打印诊断**，不给出退出码结论。
- 逐条判读规则与对账表见 `doc/08-索引与概念/全代码索引.md` §18.1。

## 怎么跑

主机上现在有 node（实测 `node -v` = v26.13.0，PATH 里就有），直接跑即可，**一律不传参数**（默认根
就是 `../../qml`；传 app 根会递归读进 `build/` 里的旧副本，量出来的数不是源码树）：

```bash
cd /d/build_docker/app/tools/qml_checks
node page_head_check.js
```

没有 node 的机器上再用 Qoder 自带的 Electron 兜底：

```bash
cd /d/build_docker/app/tools/qml_checks
export ELECTRON_RUN_AS_NODE=1
"/c/Users/Administrator/AppData/Local/Programs/Qoder/Qoder.exe" pragma_check.js
```

传根目录时**必须给 Windows 看得懂的路径**（`D:/build_docker/...`），不要给
`/tmp/...` 或 `/d/...` —— Electron 是原生 Windows 进程，`/d/x` 会被它当成
`D:\d\x`，`fs.existsSync` 直接 false，检查器一声不响地报 0 条，看起来像"全绿"。
这个坑实测踩过：拿一个故意写坏的 fixture 验 `int_prop_check.js`，前两次都返回 0，
以为脚本坏了，其实是根目录压根没被读到。**任何"0 条"结论都要先用一个已知命中的
样例反证脚本是活的。**

容器里**没有 node**（实测 `osw_reg` 里 `which node` 空），所以下面 30 个脚本只在 Windows 主机跑 ——
其中 **27 个带退出码** (0 干净 / 1 有命中 / 2 自己没跑成)，
另外 3 个 (`nav_reach_check.js` 与 `route_list_logic_check.js`、`travel_list_logic_check.js`) 不带退出码，
是人工核对 / 逻辑取证 dump。
2026-10-28 #156 之前有 5 道 (跨组件/跨文件 id、mono_cjk、pragma、悬空 id) 只打印"命中 N 处"而**永远 exit 0** ——
写成脚本串起来跑时那就是假绿，现已补齐退出码。
搬进仓库是为了进版本控制、并且根目录不再写死绝对路径；哪天容器装了 node，
直接 `node tools/qml_checks/pragma_check.js` 即可（仓库挂载在 `/project`）。

需要真正**实例化**组件树才能暴露的那一类（见下一节），不在这里，在
`tools/qml_load_check.sh`。今天这台机器上两道门禁都跑在**名为 `osw_reg` 的常驻容器**里
（镜像 tag `osw_ut:snap`，仓库挂在 `/project`；容器自带的 compose 标签是从 android-builder
继承来的，别看标签以为它跑不了桌面检查）—— 实测该镜像的 `/opt/Qt/6.7.2/gcc_64`
**有** `qml`/`qmllint` 两个二进制，**也有** QtLocation/QtPositioning/QtSensors 的 qml 模块，
所以 MapPage 起得来。compose 里 `unit-test` 那个服务名今天没在跑，用法见脚本头部。

## 加新检查器的规矩

只准读文件、打印结论，**不写任何文件**；根目录一律走 `__dirname` 相对定位，
不要写 `D:/build_docker/...` 这种绝对路径（这条就是本目录从仓库外的
`_scratch_debug/` 搬进来的原因 —— 搬进来它们才进得了版本控制）。

**判据要求「写某个属性」时，那个属性必须先被证明确实存在于这套 Qt**（2026-11-03 #46 加）。
反例是本题自己的第一版：`overlay_triad_check.js` 把「`Menu` 的 `header`/`footer` 任一处有标题」
写成 L8 的合规形状，照它补出的 `Menu { footer: ItemDelegate {…} }` 让本门禁 exit 0、
让 `qmllint` 全树 0 Error，而 Qt6 的 `Menu` 从 `Popup` 派生根本没有 `footer` ——
加载期硬错、整页编译不过、真机开局白屏，只有 `tools/qml_load_check.sh` 抓得到
（`Cannot assign to non-existent property`）。所以：

1. 新增或改判的**结构性**门禁，落地后要跑一次 `qml_load_check`（容器 `osw_reg`，
   判绿只认输出那行 `✅ 组件树加载通过`），才算闭环；
2. 每条新判据都要有 `bad/` + `good/` 两棵树：`bad/` 里每棵树**只命中预期的那一条**，
   `good/` 里放**本仓现存的合规形状**（不然判据过严会在下一轮被当成噪声绕过）。
   #46 这一轮的 `good_menu.qml` 就逼出了「一行式 `Text { text: "…"; font.bold: true }` 读不到」
   这条修订 —— 假阳性与漏检是同一枚硬币。
