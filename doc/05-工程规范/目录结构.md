## 2. 划分原则

### 2.1 按"业务领域"分,不按"技术层"分

- ❌ 不按 `services/`, `models/`, `views/`, `controllers/` 这种 MVC/MVVM 分法
- ✅ 按"用户能感知到的功能模块"分:急救 / 绳结 / 物种 / 装备 ...

理由:
- 业务模块会增删 (新增 "天气查询" → 加 weather/);技术层几乎不变
- 代码查找按业务名 (`How does SOS work?` → `lifesaver/`) 比按类名 (`Which service?` → `services/`) 更直接
- QML 端 Page 与 Service 一一对应 (`SOSPage.qml` ↔ `SOSService.cpp`),目录对齐能直接跳转

### 2.2 单文件目录保留 (不合并)

虽然 `knots/` / `survival/` / `routes/` / `travel/` / `map/` / `preparation/` 目前 Service 数 ≤2:

| 目录 | Service 数 | 论证保留 |
|---|---|---|
| `knots/` | 1 (KnotService) | 业务独立, 不会与 lifesaver 合并 |
| `survival/` | 1 (SurvivalService) | 内容专属性强 (失温/中暑/迷路 等手册), 与 FirstAid 区分 |
| `routes/` | 1 (RouteService) | 与"旅行"是 N:N 关系 (一条路线可多个旅行),独立 |
| `travel/` | 1 (TravelService) | 与 routes 是双向引用,放一起会循环 |
| `map/` | 1 (MapService) | 跨 domain (轨迹记录 / 摄影点 / 物种位置),独立模块 |
| `preparation/` | 1 (ChecklistService) | 通用清单,与"装备清单"区分 (equipment 走 JSON 只读库) |

**不合并**: 看似文件少,实则每个目录都是独立的可插拔模块,合并到 common/ 会让 common/ 变成大杂烩,违背"common 仅放跨域工具"原则。

### 2.3 `core/` 与 `common/` 区分

| 层 | 含义 | 例子 |
|---|---|---|
| `core/` | 全局基础设施 (数据库、注册中心、错误码定义) | `Database`, `ServiceRegistry`, `Result`, `Logger` |
| `common/` | 跨 service 复用的小工具 / 模板 | `DbHelper`, `SettingsStore`, `Repository`, `QueryTemplate` |

判定规则:
- 用了 ServiceRegistry / Database 等"全局概念"的 → `core/`
- 只接 QSqlDatabase / QSettings / QObject 等 Qt 原生类的 → `common/`

### 2.4 `core/internal/` 命名空间锁定

仅 `core/` 内部的辅助模块可见:
- `QmlResultBridge` — `Result<T>` ↔ `QVariantMap` 转换, `ServiceBase` 内部使用
- `internal/` 是命名空间提示, **禁止** service 或 qml include

## 3. 跨目录依赖方向

```
core ← common ← service (任何)
                  ↓
                  QML pages (同名)

禁止:
  core → service (反过来依赖)
  service → QML (service 是数据层)
```

例外: `common/ServiceBase.h` 暴露给所有 service,这是"基类"约定,不算反向依赖。
