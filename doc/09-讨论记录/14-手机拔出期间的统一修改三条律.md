## 二、逐条修复

### 1. F1-2 → 定律 L14：`FilterRow.comboRowCount` 不认包装列表（#48）

**现场**（13 号 §3.2）：路线列表 / 旅行列表的省份+月份、装备页省份、地图搜索 Tab 省份、图鉴月份 —— 七个下拉框整块空白。

**容器内量实推翻了我上一轮的推断**。13 号写的是"疑 `Array.isArray` 不认 `QVariantList`，是推断、未打印运行时类型证实"。
本轮在容器里真的打了一次，而且**做成了两条可重跑的 ctest 用例**（`tests/unit/test_common_options.cpp:249`
`cpp_qvariantlist_is_wrapped_not_js_array_in_qml` 与 `:274` `cpp_stringlist_is_wrapped_not_js_array_in_qml`），
结论比推断更怪：`Q_INVOKABLE QVariantList/QStringList` 跨进 QML 的 `var` 之后

- `typeof === 'object'` —— 对；
- **`Array.isArray()` 是 `false`** —— 所以"要么认 count、要么认 isArray"的两支它一支都不进；
- `.count` / `.get` 没有 —— 所以也不能当 ListModel 认；
- 但 `.length`、`[i]`、`[i].key`、`indexOf()`、`join()` **全都能用**，且每次调用返回一个新对象。

于是 `comboRowCount` 算出 0 → `textForRow()` 第一句 `if (n <= 0) return ""` → 显示词被吞。
同一形状还藏在 12 个详情页的 `_toArr()` 里（那些早就是"先 `Array.isArray` 早退、再按 `.length` 抄一遍"，读 `.length` 那半是对的）。

**改法**：`qml/components/base/FilterRow.qml` 的 `comboRowCount` 三元改成认 `count` 与 `length` 两支；
`qml/pages/MapPageComponents/SearchTab.qml` 的 `comboCurrentIndex` 改成 `(m && typeof m.indexOf === 'function') ? m.indexOf(root.province) : -1`。
**没有**把 12 份 `_toArr` 抽成公共 normalizer —— 它们都已经读 `.length`，律已由门禁钉住，
在没手机可验的情况下动 12 个文件的风险大于收益，这笔记成已知债。

**门禁**：新增 `tools/qml_checks/combo_shape_check.js`（第 24 道带退出码）。三条判据 + 站点数不足时 exit 2。

### 2. B 组 FAIL → 定律 L11 判据 ④：Tab 高亮读的是"请求值"不是"真实值"（#49）

**现场**（13 号 §2.3）：装备页环境条件 Tab 高亮停在「当前天气预报」，同一屏读数行写「天气手填」，chips 里装的是推演值。

**改法**（`qml/pages/EquipmentPage.qml`）：把"用户要哪一档"与"实际服务哪一档"拆成两个属性 ——
`property int weatherSource`（请求值）与 `readonly property int weatherSourceReal`（真实值），
选中态表达式一律改读后者。第一版我把公式编错过：写成"断网就降到往年推演"，
重读 13 号 §B「Tab 高亮在往年推演，但同一屏的读数行写天气手填」才确认降档方向是 `source=1 && !hasClimate → 0`。

顺带挖出**一条没记录过的同族缺陷**：`applyWeather()` 在 2→1 切换时不清 `forecastRead`，
于是 9 处显示/取数还在读预报值，而 chips 已经写着推演 —— 这就是 L11 的另一枚硬币，已补 `forecastRead = ({})` 清掉。
数据层四处（`hasEnv` / `envRead` / `mm` 那行）**故意留在 `hasForecast`**：它们问的是"这份数是不是预报来的"，不是"UI 选中哪一档"。

**门禁**：`state_truth_check.js` 加第 ④ 条 —— 检测到 `X` / `XReal` 成对声明时，任何 `X === index` 的选中态表达式必须改读 `XReal`，
且声明出来的 `XReal` 不许没人读。

### 3. A 组 FAIL / L6-1 → `page_head_check.js` 判据 ⑤：页头条高度必须 ≥ 三行自然高（#42 第二半）

**现场**（13 号 §2.2）：营地页与求助页微标签上缘 device y 283，而 band 顶 279 —— 字的上半被切掉 8 设备 px。
两条根因叠在一起：① `PageHeadBand` 的 `Column` 是 `anchors.bottom` 贴底，三行自然高 ≈56（`fsSm` 时 ≈62）> `pageHeadH`(54)，溢出只能往上冒；
② 那两页把 band 放进 `clip: true` 的视口，冒出去的部分被裁 —— 其余 9 页同样溢出，只是没有裁剪祖先。

**改法**：`Column` 给 `id: headCol`，定高改 `Layout.preferredHeight: Math.max(styles.pageHeadH, headCol.implicitHeight)`。
**不涨 `pageHeadH` 这个 token** —— 字号是 Styles 里的活值，抄一个"今天够用的数"（比如 62）下次改字号还会切，
那等于把定律绑在当前字号上。

**门禁**：`page_head_check.js` 加判据 ⑤（max 形状 + `headCol` 确有声明）。
判据 ② 查不出这一条：它只问"这行引没引 token"，而 `Layout.preferredHeight: styles.pageHeadH` 满分合规却照样裁顶。
`id` 那条刻意只查"声明存在"，不查"挂在那个 Column 上、且与 `Column {` 之间隔一个换行" ——
按换行写死就是把判据绑在排版格式上，谁把两行并成一行就误报。

### 教训一：并发跑两次构建 = 涨号被吃掉 + 交付包被改名（真 bug，本轮实测）

两轮构建**同时在同一个 `/project` 上跑**：A 于 02:58:47 把版本 `0.0.7 → 0.0.8` 写进 4 处
（`build_008.log:15-16`），B 于 03:12:35 又把它 `0.0.8 → 0.0.9` 写进同样那 4 处（`build_008b.log:15-16`）。
于是 A 的 STAGE 4 出现自相矛盾的两行：

```
[03:15:48] ✅ APK 版本回验通过: versionName=0.0.8 versionCode=8      ← 从 APK 里读出来的真值
[03:15:52]   路径: /project/dist/OutdoorSurvival-v0.0.9-release-arm64-v8a.apk   ← 复制时现读 CMakeLists
```

**A 造出来的那个 versionCode=8 的包被按 0.0.9 的名字放进了 `dist/`** —— 盘上出现"名字说 9、里面是 8"的交付包。
这不是记号问题：如果我就这么装机，看到的会是 0.0.8 的行为却报 0.0.9。
**口径**：`build_apk.sh` 的复制步骤现读版本号，而 STAGE 1 会**改写**同一个文件 ⇒ **一次只跑一个构建**，
且装机前必须用 Windows 侧 `aapt2 dump badging` 读包里的真值，而不是读日志里的"路径:"那行。
B 的产物在 03:28:13 STAGE 4 覆盖了它，现在 `dist/` 里 11:28 那个才是真正的 0.0.9。

### 教训四：把一次性取证脚本升级成门禁时，它自己的"期望 0"分支假绿过一次

`apk_rcc_probe.py` 本轮门禁化（收 `--must-hit` / `--must-be-zero`，判错 `exit 1`，没带任何 `--must-hit` 对照
直接 `exit 2`）。第一版判"期望 0"时**只数解压流、把明文区整份忽略**（当时的理由是"二进制里没法安全去注释"）。
反证 `--must-be-zero Z=pageHeadH` 报了 **OK**，而 `pageHeadH` 源树里真实存在（明文裸计数 4）⇒ **假绿坐实**。
修法：`count_outside_comments()` 每次命中回溯到本行行首，有 `//` 就不计数，**明文区与解压流两边都算**；
"期望 >0"也走同一口径（否则一句提到新写法的注释就能造假绿）。三条反证现在都过（`tmp_reg/probe_controls.sh`）：
① `--must-be-zero Z=pageHeadH` → `FAIL 去注释 2（裸计数 4）` rc=1；② 不存在的串当 `--must-hit` → rc=1；
③ 不带对照 → rc=2。**口径：正例 PASS 只证明脚本会打印绿，不证明它会变红 —— 每道新门禁都要当场跑一次"它应该会 FAIL"。**
重跑后的七条（0.0.9）：新 L14 1 / 旧 L14 **0**（注释那处已被去掉）/ 新 L6-1 1 / 旧 L6-1 0 / 新 L11④ 1 / 旧 L11④ 0 /
`clip: true` 35 ⇒ **PASS（判错 0 条）**。详 07 手册 [§12.7.1](../07-部署与发布/Docker构建APK手册.md)。

链侧证据（可与上面的包侧证据并列）：`FilterRow.qml` 10:32 / `PageHeadBand.qml` 10:49 / `EquipmentPage.qml` 10:46
都**早于** STAGE 2 起点（A 10:58:49、B 11:12:39），且卷里 `FilterRow_qml.cpp` 与 `PageHeadBand_qml.cpp`
于 **11:04 重新生成**（晚于两次编辑）。⇒ 改动进了这次构建成立，但**每一处改得对不对仍只有真机能判**。

### 另外两条

`dmesg` 未见 OOM 记录，但**同一份源码树同时跑两次构建本身就是这次的事故源** —— 结论：
**出包期间不并发构建、不并发抢内存**。
