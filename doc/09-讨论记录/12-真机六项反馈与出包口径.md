## 一、环境与出包口径（两条结论）

### 1.1 只出 arm64-v8a

用户明确: "现在的机器是 arm64-v8，其他的包不需要出"。落法:

- `build_apk.sh` 本来就默认 arm64-v8a, 不传 ABI 也只出这一个 —— 这一层没动.
- `Dockerfile.android` 里 `android_x86_64` 的 aqt 安装与 qtquick3d 的 x86_64 源码编译
  **注释掉**（不是删掉, 旁边写明怎么放开）。这两段是镜像构建时间的大头, 只出 arm64 时
  白等一遍.
- `CMakeLists.txt` 的 `ANDROID_ABIS` **不动**: 它是构建配置里唯一被反复验证过的写法,
  为了"删一个 ABI"去改它, 风险大于收益. 归档口径由脚本参数 + 镜像内容约束.
- 结论: **模拟器验证这条路关掉了** —— x86_64 模拟器跑不了 arm64 原生库. 验证只剩真机.

### 1.2 本机没有 Docker: 走 WSL2 + Docker Engine, 不用 Docker Desktop

- 本机: Windows 10 Pro 21H2, build **10.0.19044**; 已确认 `wsl.exe` 存在但没有任何发行版,
  没装 Docker.
- **Docker Desktop 4.49+ 要求 Win10 build 19045 (22H2)**, 这台是 19044 —— 装当前版本的
  Desktop 起不来; 能装的是已停更的旧版本.
- 因此选 **WSL2 里装 Docker Engine + compose 插件**, 不经 Docker Desktop:
  构建链要的只是 `docker compose build/run`, 与 Desktop 无关.
- `Microsoft-Windows-Subsystem-Linux` 与 `VirtualMachinePlatform` 两个功能已用
  `/norestart` 启用成功, **等待重启**; 重启后: `wsl --update` → 装 Ubuntu →
  WSL 内装 Engine → `docker compose build android-builder` → 出包.
- 失败时的退路: `build_apk.bat` 是 Windows 原生半成品（缺 qmlcachegen/R8 等阶段, 已知不完整）,
  不作为交付路径.

## 二、六条反馈

### 2.1 地图看不到标注的动物排序与信息

调用链: 底部五格 → ④地图 → 底栏第一个 Tab 「盘上目标」(`NearbyTab.qml`)。这一屏原来只有
"按距离排一行一行的标注 + 路线", 标注行不带危险等级、不带时间, 也**没有任何排序入口** ——
用户想"先把剧毒的挑出来"只能自己扫一遍 28 条.

改法:
- 顶部加排序 chips: **距离 / 危险 / 最近**（默认距离, 与"资源按离你多远排"的既有口径一致）。
  危险档同分时回落到距离, 最近档同刻回落到距离 —— 排序必须是全序, 否则每次重建列表顺序都在抖。
- 标注行副标题带类别 + 时间 (`MM-DD HH:mm`), 行尾加危险等级标签（有等级才出现, 用该条自己的
  色调）。时间是标注创建时刻, 老数据没有就整段不出现, 不写假时间。
- 头部读数从"N 项"细分成 **"N 标注 · M 路线"**, 一眼看出这屏由哪两类组成。
- 路线行的距离单位从 `getNearby` 的公里换成米再混排, 否则路线永远排在标注前面 (旧坑, 保持)。

> 但排序 chips 不是这条反馈的真因 —— 10-29 补完 chips, 用户在地图页仍然"看不到那一排"。
> 真因是那张底部工作台的矩形盖住了吸底导航条, 见 §4.17（修了两轮才对）。

### 2.2 轨迹加载后地图上没有线

先分清"没数据 / 数据坏 / 画了但没视野"三件事:

- **最可能的主因是 MapPage 被重建, 而选择状态只活在 MapPage 里.** `Main.openBand()` 每次切
  导航格都 `stackView.clear(StackView.Immediate)` 再 push, 底图切换失败还会
  `restartBand("map")` —— MapPage 整个销毁重建, `routeOverlays` / `trackOverlays` 跟着没了,
  名字还显示「已加载」, 地图上却没线。
- 改法: 把已选 id 提到**窗口级** (`Main.qml` 的 `mapSelRouteIds` / `mapSelTravelIds` /
  `mapSelTrackIds`), MapPage 在 `Component.onCompleted` 里用 `Qt.callLater` 恢复。
  顺序有讲究: 先处理 `pendingRouteId/pendingTravelId` 再恢复, 否则会把刚到的那条 toggle 掉。
  恢复过程用 `_selectionRestored` 门闩住持久化, 避免"恢复→回写→恢复"自激。
  这张表**不落盘**: 关掉 App 就清空, 这是"本次浏览的选择", 不是用户资产。
- 兜底加固 `addOrToggleTrack()`:
  - 点数与合法点数分开统计（`points / valid / bad`), 全是坏坐标直接报错, 不再静默画空线;
  - 同时认 `latitude/longitude` 与 `lat/lon` 两种键形（导出/导入来源不同);
  - 只有 1 个合法点时落一个点标记 (`trackMarkers`), 而不是"少于两点什么都不画";
  - `fitBoundsToRoutes()` 返回布尔, 失败（还没布局出尺寸）时 `Qt.callLater` 重试一次;
  - 落一条 `[map] 轨迹 <id>: points=… valid=… bad=… drawn=… overlays=…` 日志,
    下次真机再有问题, 一条日志就能判是"没读到点"还是"画了没对上视野"。

### 2.3 海拔/速度曲线要能缩放

`LineProfile.qml` 加**归一化视窗** `viewStart/viewEnd`（不是改数据, 只改可见区间）:

- 双指捏合: 缩放中心跟着捏合中心（`centroid`）走, 不会一放大就跳回中线;
- 单指横向拖动: 只开 `xAxis`, 竖向留给外层 ScrollView —— 图占大半屏, 竖拖必须能滚页面;
- 双击复位: 缩/移到别处之后唯一的出口;
- 最窄窗口 1/40 全程: 再窄就只剩几个真实采样, 折线会乱窜;
- 纵轴范围按**可见区间**算（放大后自动贴局部起伏）, 但刻度仍是"整数好看档";
- `TrackDetailPage` 两张图下面加一行一次性提示「双指缩放 · 单指拖动 · 双击复位」——
  能缩不能缩, 用户不会自己试出来。

Tab 栏切换/换轨迹时 `distances` 变化会 `resetView()`, 不带旧窗口进新数据。

### 2.4 「分析图」点击卡顿

`LineProfile` 是 Canvas 自绘, 原来每次 `onPaint` 都把**全部**采样点重投影一遍。一条 1.2万~2.4万
点的轨迹, 进页那一帧要画两万多条 `lineTo`, 真机上就是几百毫秒的白卡。

改法 **Envelope 抽稀**: 每个约 2px 宽的桶只留纵值**最小与最大**两个索引（按 x 顺序推入）,
顶点数封在 `~2×画布宽`。峰值点不会因为抽稀消失（桶内最大值的索引一定被保留）,
形状与"全量画"在 2px 粒度上等价。统计/读数仍走全量点 —— 抽稀只影响这根线的形状精度,
不影响任何数字。

顺手: 视野窗外的点连遍历都不做（先算 `i0..i1`), 拖动/缩放时每帧的工作量与缩放级别无关。

### 2.5 紧急联系人排版

- 名册行拆两行: **姓名 + 「主」** / **号码（等宽）+ 关系**. 原来号码横插在 RowLayout 中间
  与姓名抢宽度, 窄屏长名字一 elide 只剩一个字, 号码还把两枚动作格顶向行外。
  现在姓名 `fillWidth` + elide, 动作格永远钉在行尾。
- 行内动作从手搓 `Rectangle + MouseArea` 换成共用 `IconActionCell`（TapHandler）:
  那颗 MouseArea 按下即独占抓握, 名单一长就在行里拖不动（#105 同族）。
- 添加/编辑弹窗: 三个只有 placeholder 的输入框 → 每格上方一行小字标签 + focus 描墨线的
  输入框（与 `EquipmentPage` 表单同一套）。号码格保持数字键盘。
- **软键盘让位不自己做**: `AndroidManifest.xml` 是 `windowSoftInputMode="adjustResize"`,
  IME 弹起时窗口变矮, 居中的弹窗跟着上移. 起初写的是"按 `keyboardRectangle` 把弹窗顶上去",
  被 `typed_member_check` 拦下（Popup 上不许写 `x:`/`y:` 位置绑定, 会压过开合动画）, 而且
  在 adjustResize 下本来就是多余的 —— 改回 `anchors.centerIn`, 注释写明依据.
- ⑤求助页的联系人长按拨号本来就在（`HoldConfirmRow`, 长按 2 秒）, 这一轮没动;
  本页仍不提供"点号码就拨"（全站铁律, 见文件头规则 ①）。

### 2.6 标注弹框没有删除按钮

`markerDetailDialog` 在物种类标注下多一行「删除这条标注」(`OutlineButton`, danger 色);
点击先过一张确认框（与 `EmergencyContactsPage` 的删除确认同构: `contentItem: Text` +
`DialogFooter kind:"danger"`, `confirmCode: "不可撤"`), 确认后调
`mapService.deleteSpeciesLocation(locId)`。

- 只删这个小程序自己落的"标注"(物种 `species_locations` 表), 物种本体不受影响 ——
  文案里写明这一点, 免得读成"把这个物种从图鉴里删了";
- 成功关掉详情弹框; 失败把 `error.message` 原样 `toast.error` + `console.warn`;
- 列表靠 `dataChanged` → `Connections` 重读, 页面不自己删本地数组。

> 决定有没有 CMake 增量的是**这次出包涨没涨版本号**（涨号必清缓存），不是 ABI。
> 换 ABI 各自一份缓存，不额外花钱。完整口径见 §4.15。

只有 `VERSION_BUMP=0` 的测试包才吃得到真增量**，机器只有 i5-1035G1 8 逻辑核、WSL 分到
7.6 GB 内存（`BUILD_JOBS` 因此钉在 6，不再用 `$(nproc)`）。

### 4.3 每次出包自动 +1（用户口径"0.0.2 → 0.0.3"）

`build_apk.sh` STAGE 1 读 `CMakeLists.txt` 的 `project(... VERSION)` + `APP_VERSION_CODE`，
默认 patch +1 / code +1，一次写齐 `CMakeLists.txt`、`android/AndroidManifest.xml`、
`android/app/build.gradle` 四处，写完 6 条 grep 后置核对；STAGE 4 再用
`aapt dump badging` 拿**成品 APK** 复核 `versionName/versionCode`，不一致 `exit 1` 且不落
`dist/`。失败路径（`set -e`、`die()`、裸 `exit`）由 `trap … EXIT` 把四处恢复原值 ——
只有 APK 真进了 `dist/` 才允许留新版本号。

两个开关：`VERSION=x.y.z` 指定号（code 仍 +1）；`VERSION_BUMP=0` 本轮完全不动号。
**模拟器/测试包必须带 `VERSION_BUMP=0`**，否则测试包白吃一个发布号。

没纳入自动同步的还剩 `tests/CMakeLists.txt:7`（unit-test profile 专用，不进 APK），
它会比发布号落后一位，是已知且刻意保留的。

### 4.4 模拟器路线重开（用户选定"补 x86_64 kit + 装模拟器"）

2026-10-29 §1.1 里"模拟器验证这条路关掉了"的结论**本轮按用户要求重开**，代价与落法：

- **容器里没有 `/dev/kvm`，`/proc/cpuinfo` 一条 vmx/svm 都没有**（WSL2 嵌套虚拟化没开）——
  模拟器**不能**跑在 WSL 里，必须跑在 Windows 侧用 WHPX（`VirtualMachinePlatform` 早就为
  WSL2 打开了，hypervisor 在跑，所以 WHPX 直接可用）。
- Windows 侧原先既没有 `java` 也没有 Android SDK（只有 `platform-tools` 的 adb），所以
  `tools/` 下新增三段：`win_emulator_prereq.sh`（JDK 17 走清华 Adoptium 镜像 +
  `commandlinetools-win-11076708`，装到 `D:\build_docker\jdk17` 与 `android_sdk`，并生成
  `env_android.ps1`）→ `win_sdk_pkgs.ps1`（`platform-tools` / `emulator` /
  `platforms;android-34` / `system-images;android-34;google_apis;x86_64`，约 1.5-1.6 GB，
  全落 D 盘）→ `win_make_avd.ps1`（建 `osw_api34`，`--path D:\build_docker\android_avd`
  免得把 C 盘 `.android` 塞满；`-cores 4 -memory 2048`，`-Gpu` 可选 —— **本机实测只有
  `swiftshader_indirect` 能用**，`-gpu host` 会把 guest 卡到 adbd 无响应，见 §4.6）。
- `Dockerfile.android` 的 x86_64 两段恢复，但**位置挪了**：aqt 的 `android_x86_64` kit 安装

### 4.5 本轮新踩的五条（都写进了手册 §3.1.2）

1. **构建进行中不能编辑 `build_apk.sh`** —— bash 按字节偏移回到同一文件继续读，中途改会
   让它在错位处解析：0.0.2 那次就是"APK 已生成"之后炸出
   `line 1514: syntax error near unexpected token '2026-10-21'`，STAGE 4 整段没跑。
2. **Windows→WSL 的命令行里不要写 `$( )` / `$var`** —— Git Bash 会吃掉它们（探针输出空白、
   awk 语法错、`docker stop` 返回 15）。多变量逻辑一律落成 `tools/*.sh` 脚本，按路径调。
   同理 `cmd.exe /c` 里的 `/c` 会被当成路径改写，要 `MSYS_NO_PATHCONV=1`。
3. **`pgrep -f 'compose.*build'` 会匹配到自己** —— `wsl -- bash -c "…'compose.*build…'"`
   里那段模式串就在子 shell 的 cmdline 上，于是"构建还在跑"永远是真。判构建是否结束要看
   `docker ps` 和产物，不要靠这条。
4. **换 ABI 首次出包会死在 STAGE 3** —— `androiddeployqt --no-build` 只装依赖、**不建工程骨架**，
   arm64 能用是命名卷里攒了历史状态的假象。修法见手册 §3.1.2 坑 4（`gradlew` 桩引导 ≈20 s）。
5. **`qt_libs` 里 Qt6Core 排第几，是"能不能启动"而不是"好不好看"** —— 重排那步的 Core 判据
   写死了 `libQt6Core_arm64-v8a`，换 ABI 静默失配 → Core 掉到第 4 → 先 load 的 Charts 把 Core
   当 `DT_NEEDED` 映射进来、ART 却不对它调 `JNI_OnLoad` → `s_javaVM` 为空 → Multimedia 的
   `JNI_OnLoad` 段错误。**装包成功、splash 一闪即崩，logcat 里没有 Java 异常**，只有
   `Fatal signal 11` + `QJniEnvironment::getJniEnv()`。查这类问题一律用
   `aapt2 dump resources <apk>` 读**编译进包里**的数组顺序；容器里根 `res/values/libs.xml`
   和 AGP 生效的 `app/src/main/res/values/libs.xml` 是两份不同的文件，读错那份会得出
   "顺序明明是对的"的错误结论。

### 4.8 新发现的真 bug：CARTO 底图要 API key 了（2026-11-02，影响真机）

### 4.10 两条落盘日志链路其实都是死的（2026-11-02，影响真机排查）

起因是任务 #16 那条"Logger 默认 Debug + 每行 flush，GPS 心跳每秒落盘"的怀疑。
实测下来**结论反了**：落盘根本没发生。

**证据 1 —— 30 次注入定位，文件一行没多。** 用 `adb emu geo fix` 喂 30 秒 1 Hz 定位，
logcat 里明确打出：

```
E OutdoorDiag: [INFO] 2026-11-02 04:06:19.939 DEBUG  GPS update (qt): lat=31.230398 lon=121.473698 acc=5.0 alt=nan pool=2
```

同一时刻 `files/logs/app_20261102.log` 仍是 **4 行 / 604 字节**，且 4 行全是
`INFO [logger] Logger initialized`（= 4 次启动）。也就是说 `Logger::debug()` 一条都没进文件。

**根因：进程里有两个 `Logger` 对象，初始化的不是写日志的那个。**

- `App.cpp:132-133` 用 `m_logger = std::make_unique<Logger>()` 建了个**堆实例**，
  对它调 `initialize(dataPath() + "/logs")` —— 文件句柄开在这台机器上，
  而 `initialize()` 内部只写"Logger initialized"这一条，用的正是这个实例。
- `Logger::debug/info/warn/error` 这些静态便捷方法（全代码库都在用它们）走的是
  `Logger::instance()`（`Logger.cpp:23` 的函数内 `static Logger s_instance`）——
  **另一个对象，从来没被 `initialize()` 过**。
- 于是 `writeToFile()` 每次都撞在 `Logger.cpp:94` 的 `if (!m_logFile.isOpen()) return;`
  上静默返回。`log()` 前半段的 `qDebug()/qWarning()` 照常进 logcat，所以
  **看起来"日志在工作"，实际上只有 logcat 那半条活着**。

`Logger.h:75` 的 `m_minLevel = Level::Debug` 也确实没有任何 setter（全库 grep 只有声明
和 `Logger.cpp:78` 那一处比较），所以"级别没设过、Debug 全放行"这句是对的 —— 只是
放行之后没地方写。**"每秒 flush 落盘"这个担心可以撤掉，代价是反过来的：落盘一条没有。**

**证据 2 —— `stage0.log` 三个候选路径一个都没开起来。**

```
/sdcard/Android/data/com.outdoor.survival/files/   → 目录不存在
/sdcard/Android/data/com.outdoor.survival.debug/   → 同上
/data/local/tmp/stage0.log                          → 不存在（/data/local/tmp 里只有 dalvik-cache）
```

`main.cpp:96-112` 是"三个路径全试着 open，谁开得通用谁"，全失败 → `g_diagLogFiles` 空。
`main.cpp:88` 自己注释过 release 沙盒那条"adb pull 无权限"，但真机上的问题是更前面的
**根本没创建**。合理怀疑是 Android 11+ scoped storage 下，`QGuiApplication` 建立之前
（`main.cpp` 这段确实在 App 实例之后、Qt 平台层之前）拿不到外部存储的写权限；
`/data/local/tmp` 则是 SELinux 对 app 域不可写。这条**没有在模拟器上再往下钻** ——
两个环境的失败原因可能不同，真机上要单独验。

**合起来的后果**：release 包在**没有 adb 的真机上，目前一条日志都取不到**。
这直接顶在下一步（任务 #12 真机逐条复核）的枪口上 —— ④「分析图」卡顿、②轨迹没线
这两项最需要的就是"用户操作时设备上发生了什么"，而现在的导出日志通道是空的。

**修法（本轮未动代码，先记口径）**：`Logger` 侧是一行量级的改动 —— 让 `App` 直接用
`Logger::instance().initialize(...)`，把 `std::unique_ptr<Logger> m_logger` 这个多余的
owning 成员删掉（`App.h:100` / `App.cpp:118` / `App.cpp:132`）。singleton 本来就在，
`unique_ptr` 是重复建设。**但**它会把"每行 flush + 每行 `enforceTotalSize()` 目录扫描"
这条一直存在、此前被"没开文件"意外短路掉的开销**重新激活**，所以两件事必须一起定：
级别要不要在 release 收到 Info，以及 `enforceTotalSize()` 要不要改成按写入次数摊销。
不建议只修链路不修开销。

> **2026-11-02 更新**：这一节只是诊断，代码当时没动。三条（Logger 单例、
> `enforceTotalSize()` 的 O(n²)、stage0 路径）都已在 **§4.13** 修完并在设备上量到结果。
> 其中"开销被重新激活"这句应验了 —— 现在确实每秒落一行，所以 O(n) 那半是**必须**一起做的。
> 唯一没做的是"release 级别收到 Info"：本轮保持 Debug，先让日志把线索吐出来
> （§4.13 末尾那两条新线索就是这么来的），收到 Info 留到六项复核完再定。

### 4.15 0.0.5 出包 + 把 §4.11 那条耗时结论推翻（2026-11-02）

交付包：`app/dist/OutdoorSurvival-v0.0.5-release-arm64-v8a.apk`，**50,185,143 B**，
四阶段全绿、退出码 0，脚本自报总耗时 **7m41s**（STAGE 2 3m22s / STAGE 3 4m12s / STAGE 4 5s）。
内容是 §4.13 那三条修复（Logger 单例、stage0 四候选路径、`build_apk.sh` 机器号校验）。

不进容器直接查 APK 的独立复核：

```

native-code: 'arm64-v8a'                                   ← 单 ABI
```

（顺带记一条**复核口径**：主 .so 全文搜 `cartocdn` 现在有 **1 处命中**，但那是随 qrc 打进去的
QML **注释**文字，不是 URL。判"底图有没有回退到 CARTO"要按 `https://…` 整串匹配，
按裸关键字匹配会误报 —— §4.11 记的"零 cartocdn"就是这个意思。）

**这次把 §4.11 的耗时结论推翻了。** §4.11 说"来回切 ABI → 重新 configure → 按全冷 ≈22 min 估"，
两条都不对：

1. **构建树本来就按 ABI 分目录**：`BUILD_DIR="$APP_DIR/build/${BUILD_TYPE}_${TARGET_ABI}"`
   （`build_apk.sh:347`），卷 `app_android-build` 里 `release_arm64-v8a/` 与
   `release_x86_64/` 各有一份 `CMakeCache.txt`，**不存在"两个 ABI 共用一份缓存互相冲掉"**。
   那次 x86_64→arm64 之后重新 configure，跟 ABI 无关。
2. **真正每次都清缓存的是"自动版本号 +1"这个动作本身**。`build_apk.sh:356-363` 的三条
   `NEED_CLEAN` 判据里有一条 `[ "$APP_DIR/CMakeLists.txt" -nt "$BUILD_DIR/CMakeCache.txt" ]`，
   而版本自增改的正是 `CMakeLists.txt` 的 `VERSION` / `APP_VERSION_CODE` 两行 —— 于是
   **每一次自动涨号的出包都会清空 CMake 缓存、重跑 configure、重编全部 111 个 CXX 对象**。
   本次日志第 19–20 行如实打着：
   `CMakeLists.txt 已更新, 清理 CMake 缓存以重新配置` + `检测到 .qml 比 qmlcache 新, 清理 qmlcache 触发 qmlcachegen 重生成`。

那为什么还是只花 7m41s？因为**兜住成本的是 ccache 卷，不是 ninja 增量**。`docker-compose.yml:25`
挂了 `ccache-cache:/root/.ccache`，全量重编 111 个对象在 STAGE 2 只占 3m22s。
所以正确的估法是把"清缓存"和"冷编译"分开看：

| 场景 | 实测 | 由什么决定 |
|---|---|---|
| 自动涨号出包（默认，每次都会清 CMake 缓存） | **7m41s**（本次 0.0.5） | ccache 命中 + gradle 是否重跑 |
| 同上，但 ccache/gradle 也一起冷 | 15m2s（0.0.4 那次）**成因存疑** | 该次日志已被同名覆盖，卷里只剩 09:07 这份，无法回溯是冷在 gradle 还是冷在 ccache |
| `CLEAN=1` 全冷（Docker Desktop 时代写在 9P 上） | 24m11s | 9P 上几十万小文件，已不由这条路走 |

### 4.17 反馈① 修了两轮才对：Popup 覆盖到 = 事件覆盖到（2026-11-02）

**第一轮（只让视觉让位，不够）**：地图页那张工作台是 `edge: Qt.BottomEdge` 的 `Drawer`，
落点由 C++ 按 `popupParent.height - height` 硬算，`popupParent` 恒为**全窗口** Overlay，
于是折叠档那排「盘上目标/记录/轨迹/查找」正好压在 `Main.qml` 的 `footer: NavBands`（48 逻辑）上。
改法是 `height += navBandH` + `bottomPadding: navBandH` + background 换成"透明外壳 + 让位卡片"。
截图确认卡片抬上去了（`tmp_reg/005_sheetfix/band_sos.png`）—— 但**导航条在地图页彻底点不动了**。

**取证**（`tools/reg_sweep.sh 005_p_track`，产物 `tmp_reg/005_p_track/`）：
地图页上 BASE / SOS / ME 三格各点一次，帧一直在变（截图状态栏 11:43 → 11:44）但页面始终是地图页；
对照同一轮里 BASE→RES、RES→MAP 两跳是正常切的。再单独探（`tmp_reg/probe_band/`）：
从 `(540,2210)` 上滑 400 px，抽屉**不动** → 排除"是 `dragMargin` 那块把手带"。

**真因是两条机制叠起来**：

1. 底部 edge 的 Drawer 只能贴窗口底。容器内 offscreen 实测（`tmp_reg/drawer_probe.qml`，窗口 800 高 / 吸底条顶 752）：
   `A 裸抽屉` y=600、`B bottomMargin:48` y=600、`C parent: 内容区(752 高)` y=600 ——
   只有 `height` 动得了，落点动不了。
2. `QQuickOverlay` 是窗口最上层子项，hit-test 先问它；只要有一个**开着的** Popup 的矩形覆盖到某块区域，
   那块区域的点击就归这个 Popup，底下的 footer 收不到 —— **跟 `modal` 无关，跟 Popup 里有没有 `MouseArea` 也无关**。

所以"卡片停在导航条上方"这件事，用底部 Drawer 做出来必然是"看得见、点不动"：**矩形让不开，事件就让不开**。

**第二轮（本轮改法）**：`MapBottomSheet` 根类型 `Drawer` → `Item`，由 `MapPage` 用
`anchors.left/right/bottom` 贴在**内容区**底部 —— ApplicationWindow 的 contentData 本来就排在
header/footer 之间，内容区下沿正好是导航条上沿。连带三处收益：

- `_bandInset` / `bottomPadding` / 透明外壳那一档 hack 全部删掉；
- `MapPage.qml:1423 / 2363 / 2859` 读 `bottomSheet.height` 的三处又是真高度了（第一轮之后它们全都偏大 48）；
- 顺手修掉一块**半年死代码**：`background` 里那块铺满卡片的 `sheetShield`，与 `contentItem` 是同层兄弟
  且**先**声明，`childAt` 永远先命中 `contentItem` → 它一次也没收到过 press（"往下拖收一档"其实一直是坏的）。
  手势挪到真正的小热区：拖把那一行的 `grabTap`（点 = 换档，按住往下拖 = 收一档 / 折叠态再拖 = 关掉）。

**代价（都补了入口）**：没有 Popup 的进出场动画；没有 `dragMargin` 边缘上拉 —— 重新打开的入口是
`MapPage` 那颗常驻把手 `sheetHandle`（`visible: !bottomSheet.visible`），本来就在。

**待复核**：这一条改完必须回真机看（模拟器判不了手势手感），判据见 §4.14。

### 4.18 走查工具自己骗了一轮：模拟器会连吐陈旧帧（2026-11-02）

### 4.20 ③ 的手势在模拟器上判不了（注入通道证伪）+ 走查捞出的新真 bug：视口不裁剪（2026-11-02）

**（a）双指缩放：不是 App 的问题，是这台 AVD 收不到注入。**
`LineProfile` 的 `PinchHandler` 写了、提示文案在、`DragHandler` 的钳制也对（满视野下单指拖
是合法空操作，两次截图 md5 相同）。要判手势就得注入两点，试了两版 `sendevent` 脚本：

1. 两根手指各走一个 input 设备（event12 + event11）—— 无反应；
2. 一个设备、两个 `ABS_MT_SLOT`（0/1），带 `BTN_TOUCH` + `SYN_REPORT` 时序 —— 仍无反应。

第 2 版是 Android 多点触控的正确写法，所以做了**对照实验**：同一份脚本打到**地图页的
`MapGestureArea`**（Qt 自带的地图手势，不是本项目写的代码）上，地图**同样停在缩放 14 不动**。
`sendevent` 以 root（group `input`、context `u:r:su:s0`）写入全部成功，但事件到不了 Qt。
**结论：这台 AVD 的注入通道不支持两点手势，③ 的"缩放 / 拖动 / 双击复位"三条在模拟器上
没有判据，只能上真机。** 记下这条是为了防止下一轮再花半小时重写脚本 —— 脚本没错，通道没有。

**（b）走查撞见一个真 bug：页根高度兜底把整页撑得比视口高，内容压进底部导航条。**
在「我」这一格滚到底，段头「显示」渲染在 **y 2236–2268**，而 `NavBands` 那一条占
**2142–2274**（带顶描边实测在 y=2142）—— 字直接叠在字上。

**第一版结论是错的，值得记下来。** 当时全树扫 `clip: true`，发现 15 处视口里恰好三个页级
`ScrollView` 漏了它 —— `MePage.qml:61`、`HomePage.qml:267`、`SOSPage.qml:201`，看着就是根因
（Qt 的视口默认不裁剪，超出的一截照样画）。补上三行、门禁加断言、重出包、装机再看：
**叠字一点没变。** 裁剪的边界就是那个视口本身，而视口已经伸到带区下面去了，裁在它身上当然没用。

回到代码里找，同一批三页还有第二处共同点 —— 页根写着

```qml
height: Math.max(parent ? parent.height : 800, 800)   // HomePage / MePage / SOSPage 三页各一份
```

这行的初衷是防"parent 还没给高度"的塌陷（`layout_collapse_check` 那一类），但 **800 逻辑
比视口本身还高**：1080×2340@440dpi 上 Qt 的窗口面是 136..2274，header 占 136..272，
`NavBands` 占 2142..2274，StackView 给页的只有 **779 逻辑**（(2142−272)/2.75）。兜到 800
就等于让 `Page` 比视口高 21 逻辑，页底落到 99+800 = 899 逻辑 = **2472 设备像素**，
比窗口面底（2274）还低下去 198 px —— 滚到底时最后那一截内容正好盖在带区和系统导航条上，
量级与实测的 y 2236–2268 对得上。

**改法**：只在 parent 没给高度时兜底，不给下限 ——
`height: parent && parent.height > 0 ? parent.height : 800`（三页各一行，全树只有这三页
显式绑过页根高度）。`clip: true` 那三行**留着**：它不是这个 bug 的因，但它是仓库既有约定，
而且"视口不裁剪"本身确实是另一类真隐患。

**（c）门禁跟着加两条断言。** `tools/qml_checks/bottom_clearance_check.js`：

1. **第三遍（视口裁剪）**：`ScrollView|ListView|GridView|Flickable` 的自身属性里必须有
   `clip: true`，不写死文件名单，新页漏了直接红。反证：把 `MePage.qml:61` 那行注释掉拷进
   fixture 目录跑，命中 `pages/MePage.qml:61  ScrollView 视口没有 clip: true` + exit 1。
2. **第四遍（页根高度兜底）**：`qml/pages/` 下任何形如 `height: Math.max(parent…, N)` 的行
   直接报。反证：把 `HomePage.qml:38` 改回旧写法，命中
   `pages/HomePage.qml:38  页根用 Math.max(parent.height, N) 兜高度… clip 也救不了`。

全树现在 **33 个视口全绿**、三页高度写法全绿。

**两条口径**：① 让位（`bottomClearance`）管"末行被吸底条盖住"，裁剪（`clip`）管"内容跑到
视口外还接着画"，页根撑高（`Math.max` 兜底）管"视口本身就比屏幕低" —— 三回事，这一轮之前
门禁只有第一条，所以这个 bug 从 A41 一路活到 0.0.5。② **"共同点"不等于"根因"**：三页共同
缺 `clip` 只是相关，改完装机不复现就该回头再找一遍共同点，而不是把第一条当成已修 ——
这一轮就是靠"改完没变化"这一条否掉了自己的第一版结论。

**（d）装机复测：三页底边全部退到带区以上，叠字消失（2026-11-02 21:25）。**
装的是含高度改法的 x86_64 包（`dist/OutdoorSurvival-v0.0.5-release-x86_64.apk`，21:16 出，
versionCode 5），三页各滚到底：

| 页 | 判据 | 最低一截内容底边 | 带区顶 y=2142 | 证据 |
|---|---|---|---|---|
| ME 我 | 截图目视 | 「版本 0.0.5 · 离线数据已入库」落在 2100 以上 | 不重叠 | `tmp_reg/005_six/s34_me_fixed.png` |
| SOS 求助 | `uiautomator dump` | 「去添加」按钮 **[184,1888][436,2008]** | 差 134 px | `s36_sos_bottom.png` + `w_sos.xml` |

**坑一：构建树里的时间戳不能当证据。** 第一反应是去 `build/release_arm64-v8a/` 看

1. 日志里 `build_apk.sh` 自己那道守卫（**「检测到 .qml 比 qmlcache 新, 清理 qmlcache 触发

**坑二：`grep` 明文扫主 so 会假阴性。** Qt 6 的 rcc 是**压缩**嵌进 `.so` 的，所以
`grep -c 'parent && parent.height > 0'` 直接扫二进制 = 0，`夜晚配色`、`离线数据已入库` 也 = 0，
看起来像"包里根本没有 QML"。实际上 `bottomClearance`、`显示` 这类**进了编译字节码名字池**的串
能明文命中，源码文本只在解压后才有。取证的写法是 `tools/apk_rcc_probe.py`：在 .so 里找 zlib/zstd
魔数 → 逐块试解（本次 310 个候选、36 块解出来）→ 在解压流里数 needle。
**它同时数旧写法**，所以能给出"新 3 / 旧 0"这种双向判据 —— 只数新串不够：缓存万一没重生成，
旧串会照样躺在包里，新串也可能因为别的原因命中，双向才闭合。
