**根因（代码侧，两条叠在一起）**：

1. `qml/components/base/PageHeadBand.qml` 里那个 `Column` 是 **`anchors.bottom: parent.bottom`**，
   而 `Layout.preferredHeight` 固定 `styles.pageHeadH = 54`。三行的自然高是
   `fsXs(8.5) + 3 + fs2xl(21) + 3 + fsXs(8.5)` ≈ **56 逻辑**；状态行换成 `fsSm` 时 ≈ **62 逻辑**。
   两种都 **> 54**，所以 Column 必然向上溢出 band 顶 2~8 逻辑 px。
   量到的 279 vs band 顶 283 就是那 4 设备 px 溢出（≈2 逻辑）。
2. `HomePage.qml:268-271` 与 `SOSPage.qml:206-208` 都把 band 放在 **`ScrollView/Flickable { clip: true }`**
   里（那两行注释写得很清楚：不裁的话末段会画进底部导航条）。溢出到视口上方的部分于是被裁掉 ——
   其余 9 页溢出同样存在，只是没有裁剪祖先，所以看着没事。

⇒ 这一条正是 §4.30 A 组要判的「**顶部不裁面包屑**」，**判 FAIL**。
修法方向（留给统一修改，本轮不动）：要么 `pageHeadH` 按内容算
（`Layout.preferredHeight: Math.max(styles.pageHeadH, headColumn.implicitHeight)`），
要么把 Column 改成顶锚定并让 band 吃 `implicitHeight`；两者都要配一道门禁 ——
`page_head_check.js` 现在只查"14 个页头用没用组件 + 数有没有写死"，**查不出高度不够**，
得补一条「band 高度 ≥ 三行自然高」的静态算式检查。

### 4.1 新缺陷 F1-2：图鉴页「月份」下拉的显示值恒为空白

`62_month7.png`：页头读数行写「228 条 · 目录序 (无标注位置) · **7 月**」，列表也确实被筛成 228 条
（五味子/厚朴不见了，泽漆/苦荬菜/黄柏/射干都在），**但月份框里一个字都没有** ——
x[150,700] 逐行取样，框内每行只有 3 个暗点（左右边框），墨迹为 0。
未筛之前（`w_w_fieldguide.png`）同样是空白，本该显示「全部」。
同屏的省份框（`ListModel` 模型）正常显示「全部」。

代码侧定位（**本轮只定位，未改**）：

- `FieldGuidePage.qml:462-466` 的月份 `FilterRow` 传 `comboModel: fieldGuidePage.monthOpts`，
  而 `monthOpts = CommonOptions.monthOptions()`（:59）是 C++ `Q_INVOKABLE QVariantList`（`src/core/CommonOptions.cpp:56`）。
- `FilterRow.qml:76-79` 的 `comboRowCount` 认三种模型形态：`count`（ListModel）/ `Array.isArray`（JS 数组）/ 否则 **0**。
- `FilterRow.qml:22-33` 的 `textForRow()` 第二行就是 `if (n <= 0) return ""`。
- `FilterRow.qml:135-137` 的 `displayText` 在 `comboDisplayText` 为空时走 `textForRow(comboCurrentIndex)`。

⇒ 最可能的真因：**C++ 侧返回的 `QVariantList` 在这个调用链上没被 `Array.isArray` 认成数组**，
于是 `comboRowCount` 算出 0，`textForRow` 直接返回空串；而下拉弹层本身由 `ComboBox` 自己消费模型，
所以 13 项照常列出（`61_month.png` 里「全部/1月…9月」都在）。
省份框是 `ListModel` 走 `count` 分支，所以不受影响 —— 这正好解释了"同屏一个正常一个空白"。

### 4.1b 当晚在容器里把这条**量实了**（原写「推断」，现在作废）

不用手机也能判：`tests/unit/test_common_options.cpp` 里已有「从真 QQmlEngine 里调 C++」的通道
（`evalInQml` + `QQmlExpression`），我照着加了两条取证用例，在 `osw_reg` 容器里跑（`cmake --build build-host
--target test_common_options_test` + `ctest -R '^test_common_options$' -V`），实测读数：

| 量的东西 | `CommonOptions.monthOptions()`（`QVariantList`） | `EquipmentService.climateProvinceNames()`（`QStringList`） |
|---|---|---|
| `typeof m` | `object` | `object` |
| **`Array.isArray(m)`** | **`false`** | **`false`** |
| `m.length` | **13（可用）** | **34（可用）** |
| `typeof m.count` / `m.get` | `undefined` / `undefined` | `undefined` |
| `m[0].label` / `m[0]` | `全部`（`m[7].label` = `7月`） | `上海`（`typeof` = `string`） |
| `m.indexOf('山东')` / `m.join` | — | **`10` / 函数存在** |
| `m === m`（两次调用同一对象？） | **`false`**（每次返回新对象） | — |

⇒ **`comboRowCount` 确实算出 0**（`count` 没有、`isArray` 为假 ⇒ 落到 `: 0` 那一支），
`textForRow` 的 `if (n <= 0) return ""` 就是空白的出处；而 `m[i]` / `m[i].label` 一直是通的，
**所以错的是"行数"这一支，不是"取行"这一支**。上面 24 条用例（含新增 2 条）全过。

**这条不是新事实，是本仓早就知道、但没写成门禁的事实**：
`FieldGuideDetailPage.qml:112` 与 `KnotDetailPage.qml:58` 各有一份 `_toArr()`，
注释逐字写着「**QStringList 在 QML 端是 QQmlListModel，没有 Array.prototype 方法**」「要 filter/join 就先归一化」
（2026-09-19 就踩过）。`FilterRow.comboRowCount` 是 2026-10-29（A43）写的，**没沿用这条已知口径**；
`displayText` 改走 `textForRow` 是 2026-11-03（#40）—— 于是**修 F1 的那一刀把 1 处"显示旧值"换成了 N 处"显示空白"**。
这正是用户定的那句：定律不落成可执行检查就会漂回来，本仓现在有了最干净的一个例子。

**波及面按调用方数出来**（`grep -n 'comboModel:' qml/**/*.qml`，9 个实例）：

| 调用方 | 模型来源 | 容器实测形态 | 0.0.7 预测 |
|---|---|---|---|
| `FieldGuidePage.qml:442` 省份 | `provinceComboModel`（ListModel） | 有 `count` | **正常**（真机已判：确实正常 ✓） |
| `FieldGuidePage.qml:463` 月份 | `monthOptions()` | isArray **false** | **空白**（真机已判：确实空白 ✓） |
| `RouteListPage.qml:272` 省份 | `provinceChoices` ← `getAvailableProvinces()` QStringList | isArray false | **预测空白** |
| `RouteListPage.qml:286` 月份 | `CommonOptions.monthOptions()` 内联调用 | isArray false | **预测空白**（且每次求值新对象） |
| `TravelListPage.qml:325/339` | 同上两型 | isArray false | **预测空白** ×2 |
| `EquipmentPage.qml:1258` 省份 | `climateProvinceNames()` | **实测 isArray false** | **预测空白** |
| `SearchTab.qml:351` 省份 | `provinces` ← `getAvailableProvinces()` | isArray false | **预测空白** |

⇒ **8 个下拉里 7 个预测空白**，本轮真机只量到了图鉴月份那一格。**这是可以直接证伪的预测**，
手机插回来第一件事就是逐个开这几页看框里有没有字（比 #1 与 hero 都便宜）。

顺带同族第二处（**独立的一条，不是同一个组件**）：`SearchTab.qml:356` 写的是
`var i = Array.isArray(root.provinces) ? root.provinces.indexOf(root.province) : -1` ——
守卫恒假 ⇒ **`i` 永远是 -1**，而实测 `indexOf` 在包装列表上是**可用的**（上面量到 `indexOf('山东') = 10`）。
也就是说这一处不是"能力没有"，是"判据写错把能力挡掉了"，同一条根因的第二个症状。

修法（留给统一修改轮，本轮仍不动产品代码）：
① `comboRowCount` 补一支 `comboModel.length !== undefined ? comboModel.length : 0`；
② 把 `_toArr` 从两页复制体提成一处共享口径（它本身就是 #43 的"同类控件/同类函数一套"家族），
   `FilterRow` 进来先归一化，`textForRow` 与调用方的 `indexOf` 都吃归一化后的；
③ 可执行检查两道：`bound_model_check.js`/新加一道静态判据 —— **`qml/**` 里 `Array.isArray(<来自 C++ invokable 的值>)`
   不许当唯一判据**（至少要带 `|| typeof x.length === 'number'`），以及本文件新增的这两条 ctest 用例
   ——它们把「C++ 列表在 QML 侧 isArray=false / length 可用」钉成断言，Qt 一改转换规则就先炸。
⚠️ **口径边界**：这两条量的是 **x86_64 桌面 kit（Qt 6.7.2 gcc_64）**。它判的是 QJSEngine 的转换语义、
不是 ABI 相关代码，所以和真机 arm64 应当一致；但按本文 §一的规矩，**x86_64 的数不直接算 arm64 的证据**，
最终仍以插回手机逐格开框为准。另外 ctest 一个 QML 文件都不 load，`FilterRow` 本身的回归还得靠静态门禁。

这条是 F1 的**新形态**（#40 修的是"显示旧值"，这次是"显示空值"），同源不同症：
都是**显示口径没有单一来源**。修法方向：`comboRowCount` 不要只认 `Array.isArray`，
补一条 `comboModel.length !== undefined ? comboModel.length : 0`；
`L11` 门禁要加的是「`FilterRow` 的 `displayText` 不得依赖控件内部 `currentIndex`」——
现在这条只靠注释约束，没有可执行检查。
