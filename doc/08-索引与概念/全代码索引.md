### 3.3 Logger.h / Logger.cpp — 日志
- **6 级**：Trace/Debug/Info/Warn/Error/Fatal
- **文件轮转**：单文件 1MB / 目录总 5MB × 5 个备份
- **线程安全**：QMutex
- **存储路径**：`{appData}/logs/app_YYYYMMDD.log`
- ✅ **唯一入口是 `Logger::instance()`（2026-11-02 修）** —— `Logger.cpp:23` 的函数内
  `static Logger s_instance` 是**全代码库 240 处 `Logger::debug/info/warn/error` 静态便捷
  方法唯一走的那个对象**，任何"初始化日志"的代码都必须初始化它本身。
  这里曾经踩过一个很迷惑的坑（完整证据见 [09-讨论记录/12](../09-讨论记录/12-真机六项反馈与出包口径.md) §4.10 / §4.13）：
  `App::initLogger()` 用 `make_unique<Logger>` 建了**第二个**实例并对它 `initialize()`，
  于是单例的 `m_logFile` 永远没 open，`writeToFile()` 每次撞
  `Logger.cpp:94` 的 `if (!m_logFile.isOpen()) return;` 静默返回 —— 而 `log()` 前半段的
  `qDebug()/qWarning()` 照常进 logcat，**看起来"日志在工作"，实际落盘一条没有**。
  现在 `App.cpp:133-141` 直接 `return Logger::instance().initialize(dataPath() + "/logs");`，
  `App.h` 里那个多余的 `unique_ptr<Logger> m_logger` 成员与前向声明一并删掉。
- **`App::shutdown()` 里 `Logger::instance().shutdown()` 必须放在所有成员 reset 之后**
  （`App.cpp`）：上面几个 service 的析构里还有 `Logger::warn/error` 要先落盘再关文件。
  `shutdown()` 由 `main.cpp:354 / :371` **显式**调用，不是从析构走的，所以函数内
  `static Logger` 那时仍然活着。
- ⚠️ **`writeToFile()` 每行都会调 `enforceTotalSize()`，这条路径是热的** ——
  文件日志接通之前它永远不热（首行就 return），所以当年写成"每轮重跑一次 `totalSize()`
  闭包"的 O(n²) 没人发现。接通后每写一行都做一次目录全扫，因此改成**先算总量、删一个减一个**
  的 O(n)。**别再把它挪出 `writeToFile`**：`tests/unit/test_logger.cpp:89-121`
  （`test_total_size_limit`）就是按"每行都收敛总量"写的。
  副作用口径：现在 release 确实**每秒落一行** `DEBUG GPS update (qt)`，
  `m_minLevel`（`Logger.h:75`）仍无 setter、Debug 恒放行 —— 本轮刻意保留 Debug 换线索，
  六项复核完再考虑 release 收到 Info。
- **`stage0.log` 的候选路径**：`main.cpp` 里现在是 4 条（内部沙盒 `files/stage0.log`、
  外部 `Android/data/<pkg>/files/`、`.debug` 那一条、`/data/local/tmp/`），
  逐条试着 open、谁开得通用谁，并在日志里如实打 `log files opened: N / M`。
  **不要同时列 `/data/user/0/…` 和 `/data/data/…`** —— 两者同一 inode，
  两个 QFile 句柄开同一个文件会**每行写两遍**。
  真机上这条此前完全没创建，原因不是 scoped storage 而是**目录压根不存在**
  （`/sdcard/Android/data/<pkg>/` 在这台镜像上没有，`mkpath` 与 `open` 双双失败）。

### 9.2 装备页环境条件三源（#147/#154/#155/#166）

`qml/pages/EquipmentPage.qml` 的 `weatherSource`：`0 手填 / 1 往年推演 / 2 当前天气预报`。
三源总入口是 `applyWeather()`，**上一级拿不到就自动降一级**，读数条永远不空白：

```
手填 (0)      → 五排 chip 就是输入, 预报与推演的读数全部归零
天气预报 (2)  → readForecast() 命中 → 用预报
              → 没命中 (没服务 / 没定位 / 这一天空 / >720 min 太旧) → 记原因 → applyClimate()
往年推演 (1)  → applyClimate() (equipmentService.climateFor), 省份不在 34 省表里则读数空、
                提示切「手填」
```

三条不可省的实现约束：

1. **`pullForecast()`（发请求）与 `readForecast()`（纯读）必须分开** —— 30 分钟内命中缓存时
   `refresh()` 会**当场** `emit forecastUpdated`，若在信号处理里再发一次请求就是自己转自己。
   发请求只有两处入口：切到预报档、改了最高海拔（旧读数是按旧海拔修正的，不能当新数用）。
2. **来源句与降级原因一律赋值、不做绑定** —— #111 真机两条 `Binding loop detected`
   (`climateSrcLine` + 那条 `QQuickText.text`) 的同一条教训：块绑定的求值会写回 `Text.text`，
   文本尺寸变 → 布局把高度发回同一块 → 同一批次重入绑定。`forecastSrcLine` /
   `forecastFailLine` 因此与 `climateSrcLine` 同构，只在函数里拼好赋值。
3. **读数条按键存在性 push**（`envTiles`），预报侧一个字段缺测时整格不出现，
   不会画出 `undefined mm` —— 与「不给假读数」直接对应。

手改五排 chip 任意一档即刻把 `weatherSource` 打回 0，不留隐藏态；`generateList()` 在
自动档下若三源全无读数就**拒绝生成**并说明原因，不静默退回手填。
`RouteGearRecommendPage` 目前仍只有往年一源（`climateFor`），接预报是后续项。

### 11.4 地图视野：web-mercator 只有一个口径（2026-10-22 任务 #82）

`CommonOptions` 里的两个 `Q_INVOKABLE`（`src/core/CommonOptions.h:237` 与 `:246`）：

| API | 作用 |
|---|---|
| `metersPerPixel(lat, zoom)` | `156543.033928 · cos(lat) / 2^z` —— 比例尺与 fit bounds **共用**这一条 |
| `fitBounds(minLat, maxLat, minLon, maxLon, mapW, mapH, viewX, viewY, viewW, viewH, minZoom, maxZoom)` | 把 bbox 装进 Map 的一块**可视子矩形**，返回 `{zoom, centerLat, centerLon}`；尺寸或坐标非法返回空 map（调用方自己决定"不动视野"）|

为什么要在 C++：`MapPage.qml` 的比例尺按 mercator 算，而 `fitBoundsToRoutes()` 按
"经验公式 `z ≈ 9 − log2(km)`"算，两者差约 7 档 —— 选一条 1 km 轨迹会被放到 z≈9（视野
~200 km），线细到看不见。这同时解释了 #82 的 ②「选轨迹后地图不画线」和
③「多选轨迹后比例尺跳到 200 km」，是同一个根因，不是两个 bug。
现在 `MapPage._metersPerPixel` 和 fit 都走 C++，`fit` 内部用精确 mercator
（`z = log2(min(viewW·K/dx, viewH·K/dy))` 再 clamp 到 `Map.minimumZoomLevel / maximumZoomLevel`）。
12 个参数一律**不给默认值**：`Q_INVOKABLE` 的默认实参不进 moc 签名，QML 少传时会被填成 0。

`viewW/viewH` 是"地图减去底栏抽屉"后的可用矩形（`MapBottomSheet` 高 `min(0.6H, 409)`）：
抽屉叠在地图上，按整屏居中会把刚画好的线正好压在板子底下，所以中心要往抽屉外挪。
2026-11-02 起这里的 `H` 是**内容区**高（`MapBottomSheet` 从 `Drawer` 改成了贴在内容区底部的

### 11.5 蓝点朝向与"1 米量级"精度（2026-10-26 批次，代码侧完成，真机未验）

用户报「个人位置原点无方向指示，移动不能实时变化，同时右上方方位数据未变化」。三条独立成因：

1. **朝向只有一个来源**。原来蓝点和右上角方位盘都只吃 `compassSensor`（QCompass）。这台
   Magic5 整轮 QCompass 没出一条有效读数 → 两处一起变成"没有方向 / 数字不动"。现在
   第二来源是 `emergencyService.currentCourse`（`QGeoPositionInfo::Direction` = Android
   `Location.getBearing()`，静止时 NaN）。优先级 **罗盘 > GPS 航向**，两者都无 →
   `hasEffHeading=false`，楔形整块不画、`relativeWord()` 退回绝对 8 方位，**绝不给 0°**。
   口径见 `MapPage.qml` 的 `effHeadingDeg/hasEffHeading/headingNote`，`HomePage` 与
   `SOSPage` 的方位盘用同一条回退链。
2. **`Dial.hasFix` 被喂错了东西**。它的语义是"有朝向来源才画指针"，把位置有效性传进去
   会画出一根假正北。已改为传 `hasEffHeading`。
3. **罗盘静默**。`CompassSensor` 原来只在"无硬件"和"start 失败"两种情况下说话，硬件在、
   start 成功但 `reading()` 一直不来（或 azimuth 恒 0）时完全静默。补了首帧/无效帧/读数
   不变三条诊断 —— release 包 logcat 为空，这些进 `stage0.log`。

精度侧（同一批）：Qt 源 10 s → **1 s** + `SatellitePositioningMethods` 优先；静止时
`averageFixes()` 按 1/σ² 加权平均最近几帧，**报出去的 ± 取池内最好那一帧自己量出的 σ**
（σ/√N 无硬件依据，是假读数）；`acceptLocation()` 是 Qt 源与 Java 桥唯一的落库口，手里的
点还在 60 s 保鲜期内时，无 ± 或差 1.5 倍以上的来帧不许覆盖 —— "精度显示不上去"的真因。
逐点 ± 与高程现在落进轨迹/标注 JSON（未知则该键整条不写），界面按 C++ 放出的
`hasAltitude` / `accuracy*` 键是否存在决定整行画不画。

2026-10-22 用户提的「底部导航栏，路线修改为地图；在我页增加夜晚/白天颜色切换」，
两件事共用一套既有约束 —— **颜色只有一个来源 `CommonOptions`**，所以翻档不需要动 25 个页。

| 层 | 位置 | 做什么 |
|---|---|---|
| 状态 | `src/core/CommonOptions.h:44` | `Q_PROPERTY(bool nightMode … NOTIFY nightModeChanged)`，全站唯一开关 |
| 取值 | `src/core/CommonOptions.h:121-123` | 私有 `tone(const char* day, const char* night)`；20 个"纸与墨"色靠它，21 个属性 `NOTIFY nightModeChanged` |
| 落盘 | `setNightMode` → QSettings `ui/nightMode` | 存 C++ 侧而不是 QML：颜色属性要能 NOTIFY 重算，状态得有一个地方住 |
| 启动 | `src/main.cpp:235-239` | 在 `qmlRegisterSingletonInstance` **之前**读回，免得窗口先闪一帧白天底色 |
| Material | `qml/Main.qml:67-71` | `Material.theme: CommonOptions.nightMode ? Dark : Light`，accent/primary/background/foreground 全绑 token —— 标准件（Switch / 焦点框）跟着走，否则夜里还是浅底，一屏两 world |
| 入口 | `qml/pages/MePage.qml:259-264` | 「显示 / 夜晚配色」`Switch { checked: CommonOptions.nightMode; onToggled: … }` |

**故意不参与翻档的**：⑤ 地物图例信号色（`colorForest` / `colorWater` / `colorBlaze` /
`colorHazard` / `colorLegendAmber` / `colorPlum`）和 danger/warn/success/info 这些 `CONSTANT`
状态色，`altitudeColor()` / `difficultyColor()` 两个取色函数也一样不跟着翻档。翻了就把"橙=火、红=危险、
绿=可食"这套读法拆掉，而它们本就是中明度、深浅底都读得到（理由写在 `CommonOptions.h:40-43`）。
夜晚档也不是纯黑：`#E8ECEA → #121614`，岩面绿灰的"纸质"是这套图例的身份，黑了就成通用深色主题。

维护规矩三条：

1. 页面里**不许**再写字面 hex（现状：全站 `.qml` 只剩 3 处 `"#RRGGBB"`，且全在
   `Dial.qml` / `Section.qml` 的注释里）。
2. 新增颜色属性时先决定它属于哪一族：纸墨族 → `tone(day, night)` + `NOTIFY nightModeChanged`；
   信号族 → `CONSTANT`。把需要翻档的写成 `CONSTANT`，切档后它不重算，真机表现是
   "白天建的页留在夜晚档"，半白半黑。
3. 只改 QML 不用重编 C++，但这一轮的 `CommonOptions.h/.cpp` + `main.cpp` 是 C++ 改动，
   **APK 必须重编**才能看到日夜切换（`src/` 参与编译，见 §18.3）。

##### 18.1.1 事故：三道门禁全绿，装上手机起不来（2026-10-21）

`qmllint` 全树 0 Error、`qmlcachegen` 全过、`ctest` 24/24、APK 签名与自检全绿，
`adb install` 成功，`am start` 返回 `Status: ok` —— 然后 2 秒退回桌面。

真因只有一行：

```qml
// qml/components/base/PositionReadout.qml:128
font.pixelSize: 13.5
```

`Text.font.pixelSize` 是 **int**。给它写**字面小数**是加载期硬错误
`Invalid property assignment: int expected`，`PositionReadout` 不可用 → `HomePage`
不可用 → `Main.qml` 加载失败 → `rootObjects().size()=0` → `main.cpp` 走
`shutdown(); return -1`。`logcat` 里那条 `Fatal signal 6 (SIGABRT) ... in tid (hwuiTask0)`
是善后阶段 `pthread_mutex_lock on a destroyed mutex`，是**结果不是原因**。

三道门禁为什么都没拦住：

| 门禁 | 为什么漏 |
|---|---|
| `qmllint` | 不做字面量到属性类型的收窄；而且 `qml_lint.sh` 用的是现拼的假 `qmldir` |
| `qmlcachegen` | 只保证能编译成 C++，类型收窄发生在运行期写属性那一刻 |
| `ctest` | 单测只测 C++ service，**一个 QML 文件都不 load** |

顺带修掉的取证盲区（`src/main.cpp`）：`stage0.log` 当时只留下一句
`QQmlApplicationEngine failed to load component`，具体哪一行哪个类型全看不到。两个原因叠在一起 ——

1. 错误详情走 `qWarning()`，而 `qInstallMessageHandler` 有个"同一毫秒只留第一行"的去重
   （本意是合并多行消息的续行），引擎恰恰是同一毫秒连着吐多条，第二条起全被丢；
2. `objectCreationFailed` 用 `Qt::QueuedConnection` 挂的，但 `rootObjects` 为空时
   `main` 直接 `return -1`，事件循环根本没转起来，回调永远不执行；它写的
   `/data/local/tmp/stage1.log` 在 release 包里也没权限（一直是空的）。

现在改成 `DirectConnection` + 绕开 handler 直接逐条 `logToFile`，落 `stage0.log`。

**规则**：`font.pixelSize` / `pointSize` / `maximumLineCount` / `duration` / `interval`
这些 int 属性，**只准写整数或绑 real token**。绑 `styles.fsXs`（8.5）是安全的，Qt 会
round-half-up（实测 8.5→9、12.5→13、13.5→14）；写字面 `8.5` 就是炸。

##### 18.1.2 事故：门禁全绿，真机上一片"静默画空"（2026-10-21 真机巡检）

§18.1.1 那一类是**加载期硬错误**（整棵树建不起来，看得见）。这一类相反：文件加载成功、
qmllint 不报、qmlcachegen 不报、ctest 不报，**只有装上手机才看得见，而且是以"空白"
的形式出现** —— 没有任何弹窗，行就是没画出来。本轮巡检抓到两族：

**第一族：`pragma ComponentBehavior: Bound` 移除了视图注入的上下文属性。**
加 Bound 是为修另一件事（delegate 抓外层 id，见 `pragma_check.js`），但 Bound 语义
同时把 `model` / `index` / `modelData` 这三个上下文属性也拿掉了。delegate 里只要还在
读它们，运行期就是 `ReferenceError: model is not defined`，delegate 直接不产出内容。
实测 18 处，最狠的是 `Main.qml` 抽屉 13 行全空 —— 抽屉整个不能用，但页面是"好"的。
修法一律改成 delegate 上的 `required property var model` / `required property int index`
/ `required property var modelData`，由视图注入。

**第二族：把模块单例当上下文属性用。** 这两个来源在 `main.cpp` / `ServiceRegistry.cpp`
里是分开的：

| 名字 | 注册方式 | 需要 import 吗 |
|---|---|---|
| `xxxService`、`styles` | `setContextProperty`（上下文属性） | 不需要 |
| `CommonOptions`、`App`、`ImageColorExtractor` | `qmlRegisterSingletonInstance("OutdoorSurvival", 1, 0, …)` | **每个用到的文件都要 `import OutdoorSurvival 1.0`** |

漏那行 import，每次绑定求值抛 `ReferenceError: CommonOptions is not defined`，而失败
的 `color:` 绑定会让 `Rectangle` 停在默认值 **黑**、失败的 `font.family:` 绑定会让
`Text` 停在**系统字体** —— 所以现场看起来像"图标字体坏了""色块坏了"，真因是缺 import。
本轮的"全站图标 100% 方框"（`IconLabel` 拿不到 `iconFontReady`，永远不切 Material Icons）
和"绳结难度梯整体变黑"（`Ladder` 拿不到色）都是这一条。

两族共同的判读要点：**它们都不报错在页面上，只让东西消失或退回默认值**。所以真机巡检
必须逐页截图对着看，光看 logcat 抓不到（release 包 logcat 全空，见 `05-真机验证`）。

**门禁自查的教训**：`bound_model_check.js` 首版把 pragma 匹配写成 `^pragma`，只要行首
有缩进就整个文件跳过 —— 报"0 条"但其实是**这道门禁自己是死的**。补了负样本（一个故意
写坏的 fixture）才暴露出来，现匹配放宽成 `^\s*pragma`。这条正好重复 §18.1 末尾那条规则：
任何"0 条 / 通过"都要先用一个已知命中的样例反证脚本是活的。

##### 18.1.3 事故：加载能过、真机上一片"文字叠文字"（2026-10-22 巡检 H1 / H6）

§18.1.1 是**加载期硬错误**、§18.1.2 是**静默画空**，这一节是第三种形态：文件加载成功、
delegate 也画出来了，但**画错位置 / 一路刷非致命告警**。三道门禁里只有后加的两把 JS
检查器能拦住，qmllint 和 `qml_load_check.sh` 都不报。

**第一族：布局子项没有高度来源 → 分配高度 0 → 卡片塌陷。**
判据三条同时成立才算命中（`tools/qml_checks/layout_collapse_check.js`）：

| # | 条件 | 为什么要这一条 |
|---|---|---|
| ① | 父块是 `ColumnLayout` / `RowLayout` / `GridLayout` | 只有 Layout 会按子项的隐式尺寸**分配**高度；普通 Item 里子项自己 `height` 说了算 |
| ② | 本块类型在 `IMPLICIT_ZERO` 名单里（`Rectangle` / `Item` / `Canvas` / `Flickable` / `ScrollView` / `FocusScope` / `MouseArea`…） | `Text` / `Image` / `Row` 这类会自己撑出 `implicitHeight`，放进布局不会塌 |
| ③ | 本块**自己那一层**没有任何高度来源（`height` / `implicitHeight` / `Layout.preferredHeight` / `Layout.fillHeight` / `Layout.minimumHeight` / `Layout.maximumHeight` / `Layout.columnSpan`），且块体里出现 `anchors.fill: parent` | 子块里写 `height` 救不了父块：父块拿到的分配仍然是 0，子块只是按 0 去 fill |

`StackLayout` **不在** `LAYOUT_PARENTS` 里，所以父块是 StackLayout 的直接不判 ——
不是给它开了豁免分支，而是它本来就不会塌：`StackLayout` 强制把所有子项拉成自己的尺寸，
子项不给高度也不塌。把 `StackLayout` 加进名单会立刻造出一批假阳性。

命中过两处**同一份复制体**：`qml/pages/EquipmentPage.qml:1054`（环境条件读数条，
就是"清单页布局太差"那条反馈的真因之一）和 `qml/pages/RouteGearRecommendPage.qml:766`
（六格读数）。修法都是给外框补一行

```qml
implicitHeight: <内层 layout>.implicitHeight + 2 * styles.spSm
```

而**不是**把内层 layout 改成 `anchors.fill: parent` 之后指望它反过来撑父项 —— 折行文本的
高度要等宽度、宽度又来自本框高度，那是绑定环（`qml/components/base/Section.qml:86-88`
写的就是这件事）。`Section.qml:88` 的外框同样靠 `implicitHeight: itemsCol.implicitHeight`
给高度，所以这块也不能删。

**第二族：head/item 混排行的字段不齐 → 一路刷 `Unable to assign [undefined] to …`。**
这类列表页的 delegate 是"一个 Item 里两个 `RowLayout`"，靠
`visible: modelData.kind === "head"` 二选一。**`visible: false` 不阻止绑定求值**，
所以只要 head 行的 model 对象缺了条目行读的某个键（`tone` / `level` / `plateCode`…），
或者反过来，隐藏那一支的绑定照样会跑，真机就一路刷
`Unable to assign [undefined] to QString/QColor/int` —— 进一次列表页 206 条。
`delegate_shape_check.js` 的判据刻意收窄：只查 delegate **真的读了**的 `modelData.X`，
两边 model 字面量的键集合必须都覆盖到；注释和字符串先剥掉再匹配，且只看
`modelData.kind === "…"` 那一支所在的块，别的 Repeater（读数格之类）不算。
现在用这个 pattern 的是 9 个页 / 11 处 model 构造（ChecklistPage / DangerSpeciesPage /
EquipmentPage / EquipmentDetailPage / FirstAidPage / KnotPage / RouteListPage /
SurvivalPage / TravelListPage）。

**门禁自查的教训照旧**：这两把脚本都拿负样本反证过（2026-10-22 现跑），fixture 在仓库外

##### 18.1.7 事故：门禁全绿，「轨迹」Tab 每一行白底白字（2026-10-27 #134）

第五种形态。§18.1.1 加载期硬错误、§18.1.2 静默画空、§18.1.3 文字叠文字、§18.1.5 引用

  ② 把读数放进**仓库里的脚本**、在容器内跑（本轮用的 `tmp_reg/rc_probe.sh`：自己 `RC=$?` 再
  `echo "load_check_rc=$RC"`，同时 grep 日志里的 `加载失败` / `组件树加载通过` 行数做旁证）。
  **在同一条链上不要相信任何内联的 `$?`**。
- ⚠️ **同轮附带修正一条旧口径**：§18.1 写的"qmllint 有告警就返回 255，255 是正常值"，说的是
  **qmllint 二进制自己**；而 `tools/qml_lint.sh` 最后一行是
  `"$QMLLINT" … | grep -vE … | grep -E "^(Error|Warning|Info)"`，**脚本的退出码是最后那个 `grep` 的**
  （有匹配→0，一行都没匹配上→1，全树干净反而也返回 1）。所以 #42 那轮记的"全树 rc=255"复现不了——
  现在 `osw_reg` 与 `android-builder` 两个容器同一条命令都是 **rc=0 / `^Error` 0 行 / 上千条 Warning**，
  `255` 是当时把内层码当成了外层码。**判据只认输出里的 `^Error` 行数**，退出码无论 0 还是 1 都不作数。
- `unit-test` 镜像**没有 CMD**：`compose run --rm unit-test` 不带命令也是 rc=0，只吐 4 行日志、
  一条用例都没跑。判成功要在输出里 grep `100% tests passed`。
- `build-host` 必须是容器内的 Linux 命名卷（compose 里已挂）。指到 Windows bind mount 上，
  链出来的 ELF 会变成 0 字节，ctest 报 "Unable to find executable"。上面配方用 `/tmp/ut`
  也是同一个理由（容器自己的可写层，不碰 9P）。
- 桌面 Qt 必须带 `qtpositioning`，否则 RouteService / MapService / EmergencyService 直接 configure 失败。
- 测试进程没有 qrc，`AssetLoader` 靠 `OUTDOOR_ASSET_ROOT` 环境变量定位 `assets/data`
  （由 `tests/CMakeLists.txt` 注入 CTest）。单个用例手动跑法（可换任意资产目录，做反证用）：
  `QT_QPA_PLATFORM=offscreen OUTDOOR_ASSET_ROOT=/tmp/probe/data /project/build-host/test_asset_loader_test <function>`。

写日志的是 `src/main.cpp` 的 `logPaths`，**四条候选全试着打开，谁写得进去用谁**，
并在日志里如实打 `log files opened: N / M`（分母以前写死，2026-11-02 改成
`.arg(logPaths.size())` —— 否则加了候选、读数还是旧的，等于骗自己）；包名一律用 CMake 的

`stage0.log` 里 QML 加载失败的现场（2026-10-21 重写 `src/main.cpp` 之后才有）：

```
=== STAGE 0: QML objectCreationFailed url=qml:///... ===
  [QML error] qml/components/base/PositionReadout.qml:128:5: Invalid property assignment: int expected
```

- 每条错误**单独一行**写进 `stage0.log`。以前只 `qWarning` 一句"加载失败"，具体哪行哪个
  类型看不到，排查全靠猜。
- 为什么必须走 `logToFile` 而不是 `qWarning`：下面的消息 handler 有个"同一毫秒只留一行"的
  去重，`qWarning` 会被它吃掉。

  `objectCreationFailed` 在 Qt 6.7 只给一个 `QUrl`。**没有** `QQmlApplicationEngine::outputErrors()`，
  `errors()` 是 `QQmlComponent` 上的（按首版那样写，编译直接不过）。
